STM32F407 电控工程搭建注意事项
本文件与 agent_rules.md 配合使用；规则冲突时以 agent_rules.md 为准。
一、工程搭建总原则
先检查现有工程，再修改工程。
先建立工程框架，再逐步添加实际功能。
不得因为目录中存在某个模块，就认为该模块已经实现。
没有实际硬件依据时，不得编写具体硬件驱动。
不得为了填满目录而创建无实际用途的空文件。
所有模块必须遵守 agent_rules.md 中的架构规则。
每次修改都必须检查依赖关系和构建结果。
不得为了方便而破坏 CubeMX 原有工程结构。
不得擅自修改已经确认的架构、硬件配置和构建配置。
所有硬件参数必须有实际依据，不允许凭经验猜测后直接写入正式工程。

二、正式搭建前需要确认的硬件信息
以下信息目前尚未全部确认。
在实现对应硬件驱动之前，必须先核实。
1. MCU 与开发板
STM32 完整芯片型号。
开发板型号及版本。
MCU 封装型号。
外部晶振频率。
实际系统时钟配置。
ST-LINK 型号及连接方式。
开发板供电方式。
供电电压及各电源轨情况。
2. 电机及驱动器
步进电机型号。
步进电机驱动器型号。
步进驱动器控制接口（PUL、DIR、ENA 等）。
驱动器输入电平要求。
步进电机细分设置。
电机供电及驱动器供电。
舵机型号。
舵机供电电压及电流要求。
舵机 PWM 信号要求。
3. 通信设备
UART 通信对象。
UART 使用的具体外设。
波特率。
数据位、停止位和校验位。
是否使用 DMA。
是否使用中断接收。
实际通信协议。
数据帧格式。
CRC 校验参数。
是否存在多种通信接口。
4. 输入设备
普通按键数量。
急停按钮数量及硬件安全方案。
限位开关数量。
拨码开关数量。
各输入设备的实际接线。
输入电平及上拉、下拉方式。
是否需要硬件或软件消抖。
5. 硬件资源映射
GPIO 引脚分配。
TIM 定时器分配。
PWM 通道分配。
UART 外设分配。
DMA 通道及 Stream 分配。
中断优先级规划。
外设之间是否存在资源冲突。
注意：
以上项目不能凭空填写。
必须根据开发板原理图、芯片数据手册、外设数据手册和实际接线确认。

三、现有 CubeMX 工程检查
正式搭建目录前，必须检查已有工程。
1. CMake 检查
检查根目录 CMakeLists.txt。
确认 add_executable() 的实际目标名称。
确认工具链文件位置。
确认 CMakePresets.json 的配置。
确认编译器路径和版本。
确认 STM32 编译参数。
确认链接脚本。
确认启动文件。
确认 HAL 和 CMSIS 源文件组织方式。
确认现有工程能否正常配置和编译。
2. CubeMX 生成文件检查
检查 Core/Inc。
检查 Core/Src。
检查 Drivers/CMSIS。
检查 Drivers/STM32F4xx_HAL_Driver。
检查 main.c。
检查 stm32f4xx_it.c。
检查 stm32f4xx_hal_msp.c。
检查系统时钟配置。
检查 GPIO 初始化。
检查已经启用的外设。
3. 检查原则
不得直接重写根 CMakeLists.txt。
不得随意修改 CubeMX 生成的初始化代码。
不得擅自修改芯片型号。
不得擅自修改系统时钟。
不得擅自修改 GPIO 和外设配置。
不得重复添加 CubeMX 已经加入的源文件。
发现现有工程存在问题时，先报告，不得直接大规模重构。

四、CMake 工程搭建注意事项
1. 根 CMakeLists.txt
根 CMakeLists.txt 保留 CubeMX 原有结构。
修改前必须检查原文件。
必须确认实际构建目标名称。
只能在目标创建之后接入用户代码。
接入区域必须有明确注释。
不得猜测目标名称。
不得重复添加 CubeMX 已经添加的源文件。
2. project_sources.cmake
第一版采用显式源文件清单。
BSP 用户代码源文件。
Modules 用户代码源文件。
Application 用户代码源文件。
Common 用户代码源文件。
用户头文件目录。
规则：
新增 .c 文件必须登记。
新增头文件目录必须检查 include 路径。
不得将 tests/ 中的文件加入 MCU 构建。
不得将 Core 和 Drivers 中已经加入目标的源文件重复添加。
修改清单后必须重新配置并编译验证。
未经确认不得改为 GLOB_RECURSE 自动扫描。
3. Debug 与 Release
Debug 和 Release 应使用明确的构建预设。
检查两种配置的编译选项。
检查优化等级。
检查调试信息。
检查浮点 ABI 是否一致。
检查所有参与链接的库和目标文件是否兼容。
4. 编译产物
需要确认工程能够正确生成：
ELF 文件。
HEX 文件。
BIN 文件。
实际生成哪些文件，以工程构建配置为准。
不能将 CMake 配置成功等同于编译成功，也不能将编译成功等同于实机运行正常。

--------------------

五、目录创建注意事项
BSP
负责具体硬件驱动。
可以使用 HAL 或寄存器。
不负责比赛业务决策。
不得编造引脚和外设资源。
具体驱动必须根据实际硬件逐步实现。
Modules
不得依赖 HAL。
不得直接操作 GPIO、TIM、UART。
尽量保持算法独立。
电机操作通过 motor_if.h 抽象接口完成。
通信模块不得直接访问 UART。
算法模块应尽量支持 PC 端独立测试。
Application
负责系统初始化组织。
负责应用服务。
负责周期调度。
负责比赛状态机。
不应把所有业务逻辑堆积在 app.c 中。
Common
不依赖 HAL。
不依赖 BSP。
不依赖 Application。
提供可复用的基础组件。
应尽量支持 PC GCC 独立测试。
Config
只存放配置和资源映射。
不存放业务逻辑。
硬件映射必须经过确认。
参数必须明确单位。
未验证参数必须标注待验证。

六、重要接口与初始化注意事项
1. Board_Init()
推荐初始化顺序：
CubeMX 完成 HAL 初始化。
CubeMX 完成系统时钟配置。
CubeMX 完成所需 GPIO、TIM、UART 等外设初始化。
调用 Board_Init()。
Board_Init() 初始化所需 BSP 驱动。
Board_Init() 绑定 motor_if 等抽象接口。
确认接口函数指针有效。
注意：
底层驱动没有初始化完成，不得使用对应接口。
函数指针没有绑定，不得调用对应接口。
初始化失败必须有明确处理方式。
2. App_Init()
必须在 Board_Init() 成功之后执行。
初始化 Application 服务。
初始化 scheduler。
初始化通信服务。
初始化底盘和比赛状态机。
不得重复初始化 CubeMX 已经完成的外设。
3. App_Loop()
App_Loop() 是单次调度入口。
不得在内部创建永久循环。
由 main.c 现有 while(1) 持续调用。
每次调用执行一次应用层调度流程。
不得长时间阻塞。
不得使用 HAL_Delay() 实现周期任务中的长时间等待。
4. Scheduler
整个应用调度系统只能使用一个统一时基。
优先复用 HAL_GetTick()。
不得额外创建第二套独立毫秒计数器。
所有周期任务统一使用该时基。
必须考虑计数溢出。
必须考虑任务执行时间。
必须避免长时间阻塞。
电机 PWM、输入捕获等外设可以使用其他定时器，但不能将其作为第二套独立应用调度时基。

七、通信系统注意事项
接收方向
UART 中断/DMA
    ↓
BSP/uart（内部使用 Common/ring_buffer 缓存字节）
    ↓
Application/service/comm_service
    ↓
Modules/comm
    ↓
Application 处理解析结果
发送方向
Application
    ↓
Modules/comm
    ↓
协议组帧
    ↓
发送回调
    ↓
Application/service/comm_service
    ↓
BSP/uart
    ↓
UART 硬件
注意：
comm 不得直接调用 HALUART*。
comm 不得直接包含 bsp_uart.h。
CRC8 参数必须依据真实协议。
必须考虑接收缓冲区溢出。
必须考虑数据帧不完整。
必须考虑错误帧和 CRC 校验失败。
必须考虑连续数据帧。
必须考虑 DMA 或中断接收的缓存管理。
DMA 异步发送必须考虑发送缓冲区生命周期。
不得在中断中执行复杂协议解析或比赛业务逻辑。

--------------------

八、电机控制注意事项
步进电机
确认驱动器输入接口。
确认 PUL、DIR、ENA 的电气要求。
确认脉冲宽度要求。
确认最高脉冲频率。
确认方向切换时序。
确认细分设置。
根据控制精度和速度要求选择脉冲生成方案。
对于需要精确速度和步数控制的场景，应重点评估定时器硬件输出或定时器中断方案。
不得在没有评估的情况下，直接使用主循环频繁翻转 GPIO 产生高频脉冲。
舵机
确认舵机供电要求。
确认 PWM 周期。
确认脉宽范围。
确认角度与脉宽的对应关系。
确认舵机电源与 MCU 电源的接地关系。
不得仅凭舵机型号名称猜测所有参数。
电机接口
Modules/chassis 只通过 motor_if.h 操作电机。
BSP 提供具体电机实现。
Board_Init() 负责绑定接口。
不得让底盘算法直接依赖具体步进电机驱动。

--------------------

九、输入设备注意事项
按键需要考虑消抖。
限位开关需要考虑有效电平。
急停按钮必须考虑硬件安全措施。
急停的软件处理必须在中断或最高优先级路径直接切断电机输出，
不经过 scheduler 和状态机；状态机只做事后记录与复位。
拨码开关需要确认输入电平和读取方式。
必须根据实际接线确定 GPIO。
输入驱动只负责读取和必要的信号处理。
比赛业务逻辑由 Application 决定。
不得将急停安全完全交给普通软件轮询实现。

--------------------

十、PC 端测试注意事项
tests 使用独立 CMake 工程。
测试目标：
Common/ring_buffer（test_ring_buffer、test_ring_buffer_invalid_size、test_ring_buffer_null）。
Common/crc8（test_crc8）。
Modules/chassis/mecanum（test_mecanum、test_mecanum_extra）。
Modules/pid（test_pid、test_pid_invalid_dt、test_pid_invalid_inputs、test_pid_overflow）。
Application/scheduler（test_scheduler、test_scheduler_extra，传入模拟时间，验证到期判断、溢出、运行期保护与任务分发）。
以上 12 个可执行目标均已在 tests/CMakeLists.txt 中登记。
规则：
不引入 STM32 HAL。
不依赖 STM32 外设。
不加入 MCU 正式构建目标。
使用 PC GCC 编译和运行。
测试结果必须如实记录。
不能因为 PC 测试通过，就认为硬件驱动和实机功能已经验证通过。

十三、最终执行原则
先检查，后修改。
先搭建框架，后添加功能。
先验证底层，后集成上层。
先进行单模块测试，后进行系统联调。
硬件参数必须有依据。
所有模块必须遵守分层规则。
所有修改必须有记录。
所有测试结果必须如实报告。
不确定的地方必须先询问，不得猜测。
未经确认，不得擅自改变工程架构。
本文件与 agent_rules.md 配合使用。
agent_rules.md 负责约束 Agent 的代码修改行为；
本文件负责指导工程搭建、硬件确认、开发顺序和测试验收。
